Техническое задание на проект «Форматировщик документов по ГОСТ» (Версия 4.0: Audit & Apply с интеграцией генерации и 100% эффективностью)

1. Введение
1.1. Наименование проекта
«Форматировщик документов по ГОСТ» (кодовое название: Formatter). Режим работы: Audit & Apply (Аудит и Применение) с интеграцией модуля генерации DOCX из Markdown.

1.2. Цель проекта
Разработка программного обеспечения для диагностики и контролируемого форматирования документов Microsoft Word (DOCX) в соответствии с требованиями ГОСТ Р 21.101-2020, ГОСТ 2.105-2019 и ГОСТ 7.32-2017. Ключевое отличие от предыдущих версий: отказ от слепого перезаписывания в пользу глубокого анализа, формирования детального отчета о несоответствиях и выборочного применения исправлений пользователем. Дополнительно реализована интеграция с модулем генерации DOCX из Markdown по стандарту НТД 01-2013.

1.3. Область применения
Проект предназначен для ответственных специалистов, где критически важно сохранить смысловую структуру документа и не допустить автоматических ошибок форматирования:
• Инженеры-проектировщики (СПДС).
• Научные сотрудники и аспиранты.
• Делопроизводители государственных учреждений.
• Юристы и аудиторы технической документации.

1.4. Основные возможности (Новая логика)
• Глубокий аудит: Полное сканирование документа без внесения изменений. Сравнение каждого свойства (шрифт, отступ, интервал) с эталоном из config.yaml. 
• Детализированный отчет: Генерация списка всех найденных проблем с указанием номера страницы, номера абзаца и типа нарушения. 
• Интерактивное применение: Пользователь видит список проблем и может:
  o Применить исправление ко всем найденным ошибкам одного типа («Исправить все заголовки»). 
  o Применить исправление точечно к конкретным элементам. 
  o Игнорировать определенные типы предупреждений. 
• Безопасный режим: Исходный файл никогда не изменяется напрямую до явного подтверждения пользователем операции «Сохранить результат». 
• Визуальная подсветка: Возможность временно подсветить в документе (через выделение цветом) элементы, требующие исправления. 
• Импорт из Markdown: Конвертация Markdown-файлов в DOCX с применением стилей по ГОСТ. 
• Инициализация стилей: Подготовка документа (создание стилей, настройка полей, колонтитулов) без изменения текста. 
• Универсальная система location: Точное определение местоположения элементов (параграфы, таблицы, ячейки, колонтитулы) для гарантированного исправления.
• Поддержка таблиц: Аудит и применение стилей к таблицам, ячейкам, строкам с исправлением выравнивания, границ и отступов.
• Обработка колонтитулов: Аудит и исправление header/footer в соответствии с конфигурацией, поддержка разных колонтитулов для четных/нечетных страниц.
• Итеративное применение: Механизм повторного аудита и применения исправлений до достижения 100% соответствия ГОСТ.

2. Требования
2.1. Функциональные требования
2.1.1. Модуль Аудита (Audit Engine)
1. Построчный анализ: 
  o Проход по всем параграфам, таблицам и колонтитулам. 
  o Считывание текущих свойств: шрифт (name, size, bold, italic, color), абзац (отступы, интервалы, выравнивание), стиль (имя, базовый стиль). 
2. Сравнение с эталоном: 
  o Загрузка конфигурации из config.yaml. 
  o Для каждого элемента определяется его логический тип (на основе правил detection_rules или текущего стиля). 
  o Сравнение фактических свойств со свойствами эталонного стиля. 
  o Допуск погрешности: игнорировать различия в размере шрифта менее 0.5 пт (для защиты от плавающих конвертаций). 
3. Классификация нарушений: 
  o Критические: Несоответствие шрифта, размера, отсутствие абзацного отступа, неверный межстрочный интервал.
  o Предупреждения: Лишнее прямое форматирование, нестандартные поля, потенциально неверная нумерация.
  o Информационные: Элементы, которые соответствуют ГОСТ, но имеют нестандартное имя стиля.
4. Аудит настроек страницы: 
  o Проверка полей (левое, правое, верхнее, нижнее), ориентации, размера бумаги.
5. Аудит колонтитулов: 
  o Проверка наличия, стиля, шрифта, выравнивания.
6. Аудит рисунков: 
  o Проверка наличия подписей, соответствие стиля подписи, наличие ссылок в тексте.
7. Проверка цвета шрифта: 
  o Сравнение цвета шрифта (color) с эталоном из конфигурации. Реализовано в версии 3.0 (аудит и применение).

2.1.2. Модуль Отчетности (Reporting)
1. Формирование списка проблем: 
  o Структура записи: { ID, Тип_элемента, Страница, Номер_абзаца, Описание_проблемы, Текущее_значение, Ожидаемое_значение, Рекомендация }. 
2. Группировка: 
  o Возможность группировать ошибки по типам (например, «Все заголовки с неверным шрифтом»). [Реализована группировка по категории и важности, но не по комбинации тип+ошибка]
3. Экспорт отчета: 
  o Вывод отчета в GUI (список с фильтрами). 
  o Экспорт в текстовый файл (audit_report.txt), HTML, CSV. 
4. Сортировка по колонкам: 
  o При нажатии на заголовок колонки вся таблица сортируется в прямом/обратном порядке.
5. Цветовая кодировка строк: 
  o Красный для CRITICAL, желтый для WARNING, серый для INFO.

2.1.3. Модуль Применения (Apply Engine)
1. Выборочное исправление: 
  o Пользователь выбирает группу ошибок или конкретные ID из отчета.
  o Система применяет эталонный стиль только к выбранным элементам.
2. Умное наложение стилей: 
  o При применении стиля сохраняется содержимое текста. 
  o Прямое форматирование удаляется только в тех свойствах, которые конфликтуют со стилем (или полностью, по выбору пользователя). [Реализован выбор пользователя в фазе 1]
3. Пакетная обработка: 
  o Кнопка «Исправить всё» (применяет эталон ко всем найденным несоответствиям). 
  o Кнопка «Исправить только стили» (меняет привязку стиля, не трогая прямой форматинг). 
4. Инициализация стилей: 
  o Режим подготовки документа: создание стилей, настройка полей страницы, колонтитулов без изменения текста.
5. Повторный быстрый аудит: 
  o После применения исправлений автоматически запускать быстрый аудит для проверки результата. [Реализовано в фазе 2]
6. Оптимизация производительности: 
  o Группировка операций, кэширование для ускорения применения исправлений к большому количеству элементов. [Реализовано в фазе 2]

2.1.4. Графический интерфейс (GUI)
1. Трехпанельная структура: 
  o Левая панель: Дерево структуры документа (Заголовки, Таблицы, Списки). 
  o Центральная панель: Список выявленных нарушений (с фильтрами: Критические/Предупреждения). 
  o Правая панель: Детали выбранной ошибки и кнопки действий («Исправить», «Пропустить», «Найти в документе»). 
2. Предпросмотр: 
  o Отображение миниатюры или фрагмента текста с ошибкой.
3. Статус-бар: 
  o Прогресс аудита, количество найдено ошибок, статус готовности к применению.
4. Дополнительные функции GUI: 
  o Подсветка проблемных мест (создание копии документа с выделением цветом).
  o Поиск в документе (открытие документа с выделением конкретной ошибки).
  o Импорт из Markdown (конвертация и загрузка в интерфейс).
  o Настройка допусков (взаимозависимые поля мм, pt, twips).
  o Открытие документа/конфига для просмотра/редактирования.
  o Окно настроек игнорирования типов ошибок. [Реализовано в фазе 1]
  o Возможность сохранения с бэкапом. [Реализовано в фазе 1]
  o Кнопка «Подготовить стили». [Реализовано в фазе 1]

3.2. Описание модулей
3.2.1. config_loader.py 
• Загрузка и валидация config.yaml.
• Проверка наличия всех обязательных секций (styles, detection_rules, page_setup).
• Преобразование единиц измерения (см -> twips, пт -> twips) для внутреннего сравнения.

3.2.2. audit_engine.py (Новый ключевой модуль) 
• Класс Auditor:
  o Метод scan_document(doc): Возвращает список объектов Issue.
  o Метод detect_style(paragraph): Определяет логический тип параграфа на основе правил из конфига (регулярные выражения, ключевые слова).
  o Метод compare_properties(actual, expected): Сравнивает свойства с учетом допусков (epsilon).
• Класс Issue:
  o Поля: severity (critical/warning/info), element_id, page_number, description, current_value, expected_value, fix_action (функция-замыкание для исправления).

3.2.3. report_manager.py 
• Агрегация списка Issue.
• Методы фильтрации: get_by_severity(), get_by_style_type(), group_by_type().
• Формирование текстового представления для GUI.

3.2.4. apply_engine.py 
• Класс Fixer:
  o Метод apply_fix(issue): Выполняет конкретное исправление для одной проблемы.
  o Метод batch_fix(issues_list): Оптимизированное применение списка исправлений (группировка по параграфам, чтобы не перебирать документ многократно).
  o Логика "Safe Apply": перед изменением проверяет, не был ли элемент уже изменен пользователем вручную в текущей сессии.

3.2.5. gui_formatter.py 
• Реализация состояния машины состояний (State Machine):
  1. IDLE (Ожидание файла).
  2. SCANNING (Запуск аудита, блокировка кнопок исправления).
  3. REVIEW (Отображение отчета, активны кнопки фильтрации и точечного исправления).
  4. SAVING (Сохранение результата).

3.2.6. style_manager.py 
• Общий модуль управления стилями для ApplyOrchestrator и md_to_docx.
• Гарантированное создание стилей в документе.
• Применение настроек шрифта, абзаца, таблиц.

3.2.7. page_manager.py 
• Настройка полей страницы, ориентации, колонтитулов согласно конфигурации.

3.2.8. md_to_docx.py 
• Конвертер Markdown в DOCX по стандарту НТД 01-2013.
• Использует общие StyleManager и PageManager.

4. Алгоритм работы (Workflow)
Этап 1: Инициализация и загрузка 
1. Пользователь запускает приложение.
2. Выбирает файл DOCX.
3. Система создает копию документа в оперативной памяти (исходник на диске не трогается).
4. Загружается config.yaml.

Этап 2: Аудит (Audit) 
1. Запускается AuditEngine.
2. Проход по всему документу:
  o Для каждого параграфа определяется целевой стиль (по правилам detection_rules или текущему стилю).
  o Сравниваются фактические свойства с эталонными.
  o Найденные несоответствия регистрируются как Issue.
3. Формируется отчет и отображается в GUI.

Этап 3: Обзор и выбор (Review) 
1. Пользователь просматривает список проблем, фильтрует, сортирует.
2. Пользователь выбирает проблемы для исправления (точечно или все).
3. При необходимости пользователь настраивает параметры применения (удаление прямого форматирования, только стили и т.д.).

Этап 4: Применение исправлений (Apply) 
1. Запускается ApplyOrchestrator с выбранными проблемами.
2. Система применяет эталонные стили к выбранным элементам.
3. При необходимости выполняется повторный быстрый аудит для проверки результата.
4. Пользователь сохраняет исправленный документ (в новый файл или с бэкапом).
